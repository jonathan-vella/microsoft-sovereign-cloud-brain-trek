## Deployment types and scale

Use the current deployment-type matrix from Microsoft Learn as the baseline. The phrase "thousands of nodes" appears in connected-operations guidance, but it describes fleet scale across a sovereign environment, not a single Azure Local instance. Single-instance scale is bounded by the deployment type.

| Deployment type | Supported scale | Storage model | Design notes |
| --- | --- | --- | --- |
| Hyperconverged | 1 to 16 machines. Rack-aware hyperconverged deployments support up to 8 machines. | Compute and storage on the same machines, using hyperconverged storage. | Best for most sites that want the simplest operational model. Can run in connected or disconnected mode. |
| Disaggregated | 1 to 64 machines. | Compute and storage scale separately by using SAN storage. | Use when storage demand grows differently from compute demand. Can run in connected or disconnected mode. |
| Multi-rack | Up to 128 nodes per instance in current planning guidance, delivered as integrated racks that scale to hundreds of machines. | Main rack with network aggregation and SAN storage, plus three or more compute racks. | Requires Azure Local 2511 or later. The minimum footprint is four racks. The control plane is currently available in East US, Australia East, and South Central US ([Learn](https://learn.microsoft.com/azure/azure-local/multi-rack/multi-rack-overview)). |
| Small form factor | Compact edge appliance. | Appliance-specific compact design. | Designed for space and power-constrained sites. AI workloads and Foundry Local on small form factor are preview-only ([Learn](https://learn.microsoft.com/azure/azure-local/plan/find-your-deployment-type#workload-availability-by-deployment-type)). |

Disconnected operations is a connectivity mode, not a deployment type. Hyperconverged and disaggregated deployments can run connected or disconnected. Multi-rack and small form factor are connected-mode deployment types in the current deployment guidance.

## Rack-aware clustering

Rack-aware clustering is a two-rack Azure Local design for new deployments. It requires Azure Local 2510 or later ([Learn](https://learn.microsoft.com/azure/azure-local/concepts/rack-aware-cluster-overview)). Each rack functions as a local availability zone, and Azure Local distributes data copies across racks.

Use rack-aware clustering when a rack failure is a credible risk inside one facility or campus. It supports 2+2, 3+3, and 4+4 node layouts. You can scale by adding a pair of nodes, from 2+2 to 3+3 and from 3+3 to 4+4. The required round-trip latency between racks is 1 ms or less, and rack-aware clustering does not support external SAN configurations ([Learn](https://learn.microsoft.com/azure/azure-local/concepts/rack-aware-cluster-overview)).

Rack-aware clustering is not the same as multi-rack. Rack-aware clustering is a two-rack, direct-attached storage design. Multi-rack uses integrated racks and SAN storage for larger scale.

## Release train and support window

Azure Local changed from an annual release cadence to monthly release trains such as 2607, 2608, and 2609 ([Learn](https://learn.microsoft.com/azure/azure-local/release-information-23h2#about-azure-local-releases)). A release train can include feature builds, cumulative builds, and quality builds. New deployments currently use build 12.2609.1003.7, with availability date 2026-09-11, on OS build 26100.33438 ([Learn](https://learn.microsoft.com/azure/azure-local/release-information-23h2#supported-versions-of-azure-local)).

Keep each instance within six months of the latest release. Versions not updated within six months are unsupported, and Azure Stack HCI version 23H2 reached end of support in April 2026 ([Learn](https://learn.microsoft.com/azure/azure-local/release-information-23h2#os-version-23h2)).

## Connected and disconnected operations

Connected operations use periodic connectivity to Azure for control plane activities. Azure Local tolerates intermittent disconnections up to 30 days without affecting running workloads ([Learn](https://learn.microsoft.com/azure/azure-sovereign-clouds/private/azure-local/connected-operations-overview#what-does-connected-mean)).

Disconnected operations let an organization deploy and manage Azure Local without a connection to the Azure public cloud. Microsoft announced Azure Local disconnected operations as available in February 2026, aligned to Azure Local 2602 and later ([Microsoft blog](https://blogs.microsoft.com/blog/2026/02/24/microsoft-sovereign-cloud-adds-governance-productivity-and-support-for-large-ai-models-securely-running-even-when-completely-disconnected/)). The local control plane supports a subset of Azure Arc-enabled services, including Azure Local VMs, Arc-enabled servers, Azure Container Registry, Azure Key Vault, and Azure Policy. AKS enabled by Arc for Azure Local is listed as preview under disconnected operations ([Learn](https://learn.microsoft.com/azure/azure-local/manage/disconnected-operations-overview#supported-services)). Disconnected operations require an eligible agreement, Standard or higher support, a valid business need, Premier Solution hardware, and a dedicated management cluster.

For deeper private-cloud sovereignty design, see [Disconnected operations design](/level-200/module-07-sovereign-private-cloud-stack/disconnected-operations-design/).

## VM management tiers

Azure Local can run three VM management tiers:

| VM type | How it is created or connected | Azure management scope |
| --- | --- | --- |
| Azure Local VMs enabled by Azure Arc | Created through the Azure Local VM provisioning flow, registered to an Azure Arc resource bridge, and installed with the Azure Connected Machine agent. | Lifecycle management plus Arc extensions, monitoring, security, policy, and configuration management. |
| Arc-enabled servers | Existing servers or VMs with the Azure Connected Machine agent. | Monitoring, security, extensions, and policy. No Azure Local VM lifecycle management. |
| Unmanaged VMs | Created with local tools and not connected to Azure. | No Azure management. |

Conversion from an Arc-enabled server or unmanaged VM to an Azure Local VM is not supported ([Learn](https://learn.microsoft.com/azure/azure-local/concepts/compare-vm-management-capabilities#types-of-vms-on-azure-local)). For Azure Local VMs, manage lifecycle operations through Azure portal or Azure CLI unless Microsoft documents a local-tool operation as supported.

## AKS on Azure Local

AKS on Azure Local support follows the Azure Local release train. For release 2602 through 2607, supported Kubernetes versions are 1.31.12, 1.31.13, 1.32.8, 1.32.9, 1.33.4, and 1.33.5 ([Learn](https://learn.microsoft.com/azure/aks-hybrid-edge/supported-kubernetes-versions#aks-supported-kubernetes-minor-and-patch-versions-per-release)). Kubernetes 1.30 is no longer supported.

Starting with the 2510 AKS on Azure Local release, KMS v2 is enabled by default on new cluster deployments. Existing clusters continue to use KMS v1 ([Learn](https://learn.microsoft.com/azure/aks-hybrid-edge/local/hyperconverged/encrypt-etcd-secrets#kms-v2-on-azure-local-2510-and-later)). Current training should assume Azure Linux 3.0 for new AKS planning, because Azure Linux 2.0 reached end of life on July 31, 2025 in the current research matrix.
