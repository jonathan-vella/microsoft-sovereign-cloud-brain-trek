Microsoft Sovereign Cloud is the current name for the portfolio formerly called Microsoft Cloud for Sovereignty. The portfolio has three deployment models: Sovereign Public Cloud, Sovereign Private Cloud, and National Partner Clouds.

![Three-column diagram of Microsoft Sovereign Cloud models, showing the operator, location, and building blocks for Sovereign Public Cloud, Sovereign Private Cloud, and National Partner Clouds.](/images/level-100/sovereign-cloud-models-2026.svg)

## The terminology trap

Microsoft documentation uses "sovereign cloud" in two ways. Older Azure documentation often used **Azure sovereign clouds** to mean separate cloud environments such as Azure Government or Azure operated by 21Vianet. Current Microsoft Sovereign Cloud documentation uses the term for a broader portfolio of deployment models.

This module uses the current portfolio meaning. When you read older guidance, check whether it describes an isolated Azure environment or the current Microsoft Sovereign Cloud portfolio.

## The three deployment models

**Sovereign Public Cloud** is Azure public cloud with sovereignty controls inside defined geopolitical boundaries. Microsoft operates the datacenters, and customers use controls such as Data Guardian, External Key Management, confidential computing, Azure Policy, Sovereign Landing Zone, Customer Lockbox, and Sovereign Control Panel. The EU Data Boundary is one example of a geopolitical boundary used by the public-cloud model.

**Sovereign Private Cloud** runs on infrastructure the customer owns and manages. It uses Azure Local as the platform for customer-operated workloads and includes Microsoft 365 Local, GitHub Enterprise Local, and Foundry Local on Azure Local. This model is used when the requirement is local operation, dedicated infrastructure, intermittent connectivity, or fully disconnected operation.

**National Partner Clouds** combine Microsoft technology with partner-operated and jointly governed operations. The model is for countries or regions where a national partner must operate the cloud or participate in governance. Current Microsoft Learn pages name Bleu in France and Delos Cloud in Germany.

## Comparison

| Question | Sovereign Public Cloud | Sovereign Private Cloud | National Partner Clouds |
|---|---|---|---|
| Who operates it? | Microsoft operates Azure public-cloud regions. | The customer operates the Azure Local environment, often with certified hardware and partner support. | A national or regional partner operates the cloud with Microsoft technology and joint governance. |
| Where does it run? | Microsoft datacenters inside defined geopolitical boundaries, such as the EU Data Boundary. | Customer-owned infrastructure in the customer's datacenters and sites. | Partner datacenters inside the target country or region. |
| What connectivity does it assume? | Connected cloud service. | Connected, intermittently connected, or disconnected operation. | Connected service, with service availability and latency set by the partner cloud. |
| Main building blocks | Azure regions, Sovereign Landing Zone, Azure Policy, Data Guardian, External Key Management, confidential computing, Customer Lockbox, and Sovereign Control Panel. | Azure Local, Microsoft 365 Local, GitHub Enterprise Local, Foundry Local on Azure Local, and local operations tooling. | Microsoft cloud technology, partner operations, local governance, and national compliance targets. |
| Current status | Current model for regulated workloads in Azure public cloud. | Current model. Component status varies. For example, [Microsoft 365 Local is generally available](https://learn.microsoft.com/azure/azure-sovereign-clouds/private/m365-local/microsoft-365-local-overview), while [GitHub Enterprise Local](https://learn.microsoft.com/azure/azure-sovereign-clouds/private/github-local/github-local-overview) and [Foundry Local on Azure Local](https://learn.microsoft.com/azure/azure-sovereign-clouds/private/foundry-local/overview) are preview. | [Bleu and Delos Cloud are still being built](https://learn.microsoft.com/azure/azure-sovereign-clouds/partner/overview-national-partner-clouds) and are not global Azure regions. |

## How to choose at a high level

Start with the requirement that cannot move. If the workload can run in Azure public regions and the main concern is data residency, key control, access oversight, or policy enforcement, start with [Sovereign Public Cloud](/level-100/module-02-cloud-models/sovereign-public-cloud/).

If the workload must run on infrastructure the customer controls, or if it must keep operating without Azure connectivity, start with [Sovereign Private Cloud](/level-100/module-02-cloud-models/sovereign-private-cloud/).

If a law, policy, or procurement rule requires a national operator or a jointly governed partner cloud, evaluate [National Partner Clouds](/level-100/module-02-cloud-models/national-partner-clouds/). Service scope can differ from global Azure, so do not assume that a service available in global Azure is available in a National Partner Cloud.

Many organizations use more than one model. For example, a customer may keep collaboration and DevOps on Sovereign Private Cloud while placing analytics workloads in Sovereign Public Cloud. The model decision should follow data classification, legal constraints, connectivity, operations, and service availability.
