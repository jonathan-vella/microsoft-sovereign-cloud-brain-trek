A service model says how much of the stack the provider runs for you. The three models are infrastructure as a service (IaaS), platform as a service (PaaS), and software as a service (SaaS). NIST SP 800-145 defines all three, and every major provider uses the same names.

<LearningObjectives>
- Describe IaaS, PaaS, and SaaS and give an example of each.
- Pick a service model for a simple scenario.
- Explain the shared responsibility model and name the responsibilities you always keep.
</LearningObjectives>

## Infrastructure as a service (IaaS)

IaaS gives you the most control and the most work. The provider maintains the hardware, the network connection to the internet, and physical security. You install, configure, and patch the operating system, and you configure the network, databases, and storage. In effect you rent hardware in the provider's datacenter.

Azure examples are Azure Virtual Machines, Azure Disk Storage, and virtual networks.

Common IaaS scenarios:

- Lift-and-shift migration. You build cloud resources that look like your on-premises servers and move the workloads across with few changes.
- Development and test. You copy an established configuration, start it when a team needs it, and shut it down afterward.

## Platform as a service (PaaS)

PaaS sits between IaaS and SaaS. The provider also runs the operating system, middleware, development tools, and managed runtimes. You don't license or patch the operating system or the database engine. You bring the application code and the data, and you control who has access.

Azure examples are Azure App Service, Azure Functions, Azure SQL Database, and Azure Storage.

Common PaaS scenarios:

- Development framework. Developers build on platform components and get scaling, high availability, and multitenancy without writing that code themselves.
- Analytics and business intelligence. Teams use hosted tools to analyze data and find patterns.

## Software as a service (SaaS)

SaaS is a finished application that you rent. It's the easiest model to start with and the least flexible. The provider runs almost the whole stack, including application updates. You manage your data, user access, and the devices that connect.

Microsoft 365 and Dynamics 365 are SaaS. Email, messaging, productivity, and finance applications are typical SaaS uses.

## Compare the three models

| | IaaS | PaaS | SaaS |
|---|---|---|---|
| You manage | Operating system, runtime, applications, data, access | Application code, data, access | Data, users, devices |
| Provider manages | Hardware, physical network, physical security, hypervisor | Everything in IaaS, plus the operating system, middleware, and runtime | Everything in PaaS, plus the application |
| Flexibility | Highest | Medium | Lowest |
| Effort to run | Highest | Medium | Lowest |
| Azure example | Azure Virtual Machines | Azure App Service | Microsoft 365 |

Many solutions mix models. A company might use Microsoft 365 for email and documents, run a customer portal on Azure App Service, and keep an older line-of-business application on Azure Virtual Machines until it can be rewritten.

## The shared responsibility model

In your own datacenter you own the whole stack, from the building to the data. In the cloud the provider takes over some layers. The **shared responsibility model** says which layers belong to you, which belong to the provider, and which you share. The split depends on the service model.

| Responsibility area | On-premises | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Customer data | Customer | Customer | Customer | Customer |
| Configurations and settings | Customer | Customer | Customer | Customer |
| Identities and users | Customer | Customer | Customer | Customer |
| Client devices | Customer | Customer | Customer | Shared |
| Applications | Customer | Customer | Shared | Shared |
| Network controls | Customer | Customer | Shared | Provider |
| Operating system | Customer | Customer | Provider | Provider |
| Physical hosts | Customer | Provider | Provider | Provider |
| Physical network | Customer | Provider | Provider | Provider |
| Physical datacenter | Customer | Provider | Provider | Provider |

The table follows the Azure responsibility matrix on Microsoft Learn, with "Microsoft" shown as "Provider".

### What you always keep

Whatever the service model, you're responsible for:

- Your data, including how you classify it, protect it, and decide whether to encrypt it.
- The devices that connect to your cloud services, such as laptops and phones.
- Accounts and identities: creating users, removing them when they leave, and controlling what they can do with role-based access control, multifactor authentication, and Conditional Access policies.

### What the provider always keeps

In every cloud model the provider is responsible for the physical datacenter, the physical network, the physical hosts, and the hypervisor.

### An example

Suppose you need a SQL database. If you install SQL Server on an Azure VM (IaaS), you patch the operating system and the database engine and you protect the data. If you use Azure SQL Database (PaaS), Microsoft maintains the database engine, and you're still responsible for the data you load into it and for who can read it.

:::note[Responsibility is not the same as liability]
Microsoft Learn uses "responsibility" in a governance sense: who configures, operates, and monitors each control. It doesn't change the terms of your agreement with the provider.
:::
